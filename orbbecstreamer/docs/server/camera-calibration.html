Camera pose calibration

Print the ChArUco board, calibrate where each depth camera sits, and read the calibration state at startup.

View as MarkdownOpen in GitHub

Last updated on

Camera pose calibration measures where each camera sits relative to the others, so clients can merge all views into one 3D scene. You show a printed board to the cameras, and the server saves one pose per camera to a file.

The server needs a valid camera pose before it offers media to clients. The local pipeline (capture, GPU processing, encoding, debug recording) runs with or without one.

Before you start

You need:

  • the server built (see Build the server),
  • the cameras connected, with no other process using them,
  • streams.alignment: color_to_depth in the live config (the dev default),
  • a printer for the board, and a flat, rigid backing to mount it on.

Print the board

The board is a ChArUco board: a chessboard whose white squares hold ArUco markers (small black-and-white codes). The markers let the server identify every corner, even when the board is only partly in view.

  1. From the server/ folder, write the board as a PNG, using the board settings from your config:

    This command does not open the cameras. Without --live, it uses the built-in defaults, which are the same 7 × 5 board with 80 mm squares. The default board looks like this:

  2. Read the physical size from the log:

  3. Print the board at that size. The image is drawn at 300 dpi with one white square of margin on every side. The default image is therefore 720 × 560 mm (8504 × 6614 pixels):

    • The whole image needs A1 paper (841 × 594 mm).
    • A2 (594 × 420 mm) fits only the 560 × 400 mm board, so crop the margin or print edge to edge.
    • The PNG carries no DPI information. Set the print size yourself so that the board, without the margin, measures the size in the log.

  4. For a smaller printer, shrink the squares in the config and go back to step 1. For example, square_length_m: 0.04 and marker_length_m: 0.03 give a 280 × 200 mm board (360 × 280 mm with margin), which fits A3 landscape. Hold a smaller board closer to the cameras: it is harder to detect at the 640 × 576 depth resolution.

  5. Measure one printed square with a ruler. Put the measured size into calibration.board.square_length_m, and scale marker_length_m by the same factor. A wrong size does not stop detection, but every distance between cameras comes out scaled by the error.

  6. Mount the print on something flat and rigid. A bent board makes the cameras disagree.

Run a calibration

  1. Stop any other process that uses the cameras, such as a running orbbec_streamer --live.

  2. From the server/ folder, start the live pipeline with the calibration flag:

    The server takes the setup lock (only one client, or the console, can change the setup at a time) and starts a calibration run. This works with autocalibrate: false, and it also replaces an existing valid pose.

  3. Walk the board through the capture area:

    • Keep the board in view of at least two cameras at the same moment.
    • Move or tilt it between views. A view counts only if the board moved at least 2 cm or turned at least 3° since the last accepted view.
    • Tilt it rather than holding it face-on to a camera. The server rejects views where the board's pose is ambiguous.
    • Every camera needs at least 5 consistent views shared with a camera that is already placed. A camera that never sees the board together with the reference camera is placed through other cameras.

    The run needs 20 accepted views and gives up after 120 seconds.

  4. Wait for the committed line in the log (see Expected result). The server then saves the poses, raises the revision by one and releases the setup lock. The live pipeline keeps running.

  5. Stop the server with Ctrl+C. If you press Ctrl+C before the result is saved, the previous calibration file stays untouched.

Expected result

While the run is going, a progress line appears every 5 seconds:

cam1=no board means that camera does not see the board in the current frame.

Check the translations against the real rig. They are the positions of each camera's depth sensor, in metres, relative to the reference camera.

What the result means

Each camera gets one rigid 4 × 4 transform, serverFromDepthCamera: the pose of that camera's depth sensor in the server's coordinate frame. The server frame is the depth frame of the reference camera (the first camera in the config), so the reference camera's pose is the identity.

The server finds the board in each camera's colour image. That image is already aligned to the depth image (this is what streams.alignment: color_to_depth does), so the server solves the board pose with the depth camera's intrinsics. The result is the depth-sensor pose directly, with no colour-to-depth correction.

The saved file

The result goes to calibration.camera_pose_path. The matrix is column-major, in metres, so the last column (entries 12–14) is the translation:

The server writes a temporary file, flushes it to disk and renames it over the old one, so a crash leaves either the old or the new calibration. It only writes a result that covers every active camera with a valid rigid pose. Do not edit the file by hand: the loader is strict, and an unknown key or a non-rigid matrix makes the whole calibration stale.

Startup states

At every start, after the cameras are open, the server loads calibration.camera_pose_path, checks it against the running cameras and logs one line:

Calibration stateWhenPhase in the log
validThe file covers every active camera with the same serial number and depth resolution.READY (or STREAMING once media is requested)
missingNo file.NEEDS_SETUP, or WAITING_FOR_CALIBRATION with autocalibrate: true
staleThe file is unreadable or invalid, or a camera is not in it, has a different serial number (hardware swapped) or a different depth resolution. The reason is in the log line.Same as missing
runningA calibration run is in progress.CALIBRATING
failedThe last run failed and there was no valid calibration before.Same as missing

A missing or stale calibration never stops the server: it starts and waits for setup. Removing a camera from the config does not invalidate the others, because entries for cameras that are not running are ignored.

WAITING_FOR_CALIBRATION and CALIBRATING are log names only; clients never see them. A client sees readiness=needs-setup with autocalibrate=true instead of the first, and a camera-pose calibration in state running for the second. Setup state has the full mapping.

What autocalibrate changes

  • false (dev default): with a missing or stale pose, a client may not start a calibration. An operator runs --calibrate-camera-pose on the server.
  • true: a client that holds the setup lock may start the calibration itself, and the server holds back normal media until the result is committed. No client can connect yet, so today the only visible difference is WAITING_FOR_CALIBRATION instead of NEEDS_SETUP in the log.

In both modes a valid pose may be recalibrated. Only one client (or the console) can hold the setup lock at a time, and other clients keep their normal control connection.

Recalibrating a valid setup

While a new run is in progress, the committed poses stay in use and the server stays ready (media is paused for setup). If the run fails, the old poses stay valid and the state carries the message last calibration attempt failed: .... A cancelled or interrupted run leaves the previous calibration and its revision unchanged.

Progress shows camX=no boardThe board is too small or too far away, there is glare, the light is too low, or board.dictionary or the square counts do not match the print. Move closer, avoid reflections and check the config.
Corners detected but observations do not increaseA view is rejected when fewer than 8 corners are found, when the fitted pose is more than 2 px off on average (RMS reprojection error), or when the pose is ambiguous (small, distant or face-on board). Views also need two cameras at once and at least 2 cm or 3° of movement since the last one.
